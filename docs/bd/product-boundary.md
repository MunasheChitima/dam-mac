# Product boundary: dam-mac vs FindandSeek

This file exists to prevent future pitch drift.

## Use this product in the Canva/Pexels and visual-library pitch

### dam-mac

dam-mac is:

- a digital asset management product
- built around a custom visual indexing engine
- focused on images, visual assets, and content libraries
- about helping people search, reuse, and create from what they already have
- MCP-native, so assistants and AI-assisted workflows can call into the library
- productized on Mac first, but not limited to Mac as a capability
- trained on Linux and suitable for server-hosted deployment

Use dam-mac when the pitch is about:

- Canva
- Pexels
- visual asset libraries
- brand and campaign reuse
- creating from existing assets before generation
- reducing unnecessary image generation

## Do not use this product in the Canva/Pexels pitch

### FindandSeek

FindandSeek is a separate product.

Do not bring it into this pitch when discussing Canva, Pexels, or visual DAM.

Do not use language such as:

- local-first file intelligence
- document memory
- agent memory
- file intelligence for code, email, and documents
- generic file search or document retrieval

If a draft starts sounding like document understanding, agent memory, or
general file intelligence, it has crossed the product boundary.

## The safe positioning sentence

Use this as the default:

> dam-mac is a DAM product with a custom visual indexing engine that helps people
> search, reuse, and create from the image and content libraries they already
> have.

## MCP note

It is fine to mention MCP in this pitch, but keep it tied to dam-mac's role:

> dam-mac is already MCP-native, which means the visual library capability can
> pair naturally with AI-assisted workflows that need to retrieve the right
> existing asset before generation.

Do not let MCP drag the pitch back into FindandSeek-style agent-memory
positioning.
